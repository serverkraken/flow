PackageInfo synchron injizieren

Fix für die Produktionsstörung „Deine App-Version ist zu alt" beim Spiel-Erstellen und -Beitreten mit App 0.46.3. Von Soenne freigegeben (Option A, 05.08.2026). Root Cause ist bestätigt — nicht erneut diagnostizieren.

Root Cause — bestätigt 05.08.2026, Fable-Session

Der Bug ist ein Riverpod-Lifecycle-Problem, KEIN Android-Problem. Die frühere Diagnose „packageInfoProvider erreicht auf Android nie den data-Zustand" war ein Fehlschluss — die Versionszeile auf dem Handy wurde vermutlich übersehen, 10 px bei 30 % Alpha.

Ablauf:

  1. Tap auf „NEW GAME (Host)" → lobby_screen.dart _createSessionAndJoin() setzt _isLoading = true → der Body ersetzt JoinCreateView durch den Spinner.
  2. Die Versionszeile (Consumer unten in join_create_view.dart) ist der einzige ref.watch-Listener des packageInfoProvider — der ist autoDispose. Unmount → Provider disposed.
  3. LobbyService.createSession() läuft weiter: Session-Insert → GPS-Fix → createHostPlayer(clientVersion: _clientVersion()).
  4. _clientVersion() = ref.read(packageInfoProvider).value?.version → erzeugt einen frischen Provider im AsyncLoading-Zustand → .value == null.
  5. Server-Trigger check_session_lobby_status: is_client_version_at_least(NULL, '0.46.2') → Fail-safe false → RAISE 'err_client_version_too_old'.

Gleicher Mechanismus im Join-Pfad. Betrifft alle Plattformen. Der Bug existiert seit jeher, wurde aber erst scharf, als S12 (0.46.2, breaking-client: yes) min_client_version von 0.0.0 auf 0.46.2 hob. Erklärt auch die Geister-Lobbys: Session-Insert gelingt, Spieler-Insert scheitert danach.

Beweise:

  • Exakte Prod-APK 0.46.3 (GitHub Release Asset) im Emulator Medium_Phone_API_36.1: zeigt „Version 0.46.3+78" und bekommt beim Erstellen trotzdem den Fehler.
  • Lokale podman-DB (supabase_db_strassenfuchs): is_client_version_at_least('0.46.3','0.46.2') = true, (NULL,'0.46.2') = false, ('0.46.3','v0.46.2') = false — die v-Prefix-Falle, hier aber nicht die Ursache; bin/schema-target.sh strippt das v korrekt.
  • min_client_version in Prod = 0.46.2, früher verifiziert via app_config und Deploy-Log.

Fix — Option A, freigegeben

PackageInfo beim App-Start auflösen und synchron injizieren, exakt nach dem existierenden localStorageProvider-Muster.

  1. lib/src/shared/providers.dart: packageInfo von @riverpod Future<PackageInfo> umstellen auf sync + keepAlive, Muster aus local_storage_provider.dart:
    lib/src/shared/providers.dart · dart
    @Riverpod(keepAlive: true)
PackageInfo packageInfo(Ref ref) {
  throw UnimplementedError('packageInfo must be overridden in main()');
}
  2. lib/main.dart: nach SharedPreferences.getInstance() auch PackageInfo.fromPlatform() awaiten und in die ProviderScope-overrides aufnehmen. Defensiv: try/catch mit Fallback-PackageInfo (leere Strings) plus developer.log — ein Plattform-Fehler darf den Start nicht killen; eine leere Version wird serverseitig sauber abgelehnt statt still null zu sein.
  3. Call-Sites anpassen — alle drei, mehr gibt es nicht:
    • lobby_service.dart, Provider-Wiring am Dateiende, ~Z. 300: clientVersion: () => ref.read(packageInfoProvider).version
    • lobby_screen.dart ~Z. 426: ref.read(packageInfoProvider) ohne .value, Null-Check entfällt.
    • join_create_view.dart ~Z. 122–137: Consumer vereinfachen, .when entfällt komplett — damit verschwinden die stummen loading:/error: → SizedBox()-Zweige ersatzlos, die den Bug zwei Sessions lang unsichtbar gemacht haben.
  4. build_runner für providers.g.dart laufen lassen.
  5. Tests (TDD): Zuerst der Regressionstest, der auf dem alten Stand ROT ist — Container mit echtem Wiring, packageInfoProvider-Watcher subscriben, Future auflösen lassen, Subscription schließen, Mikrotask-Queue drehen, dann via lobbyServiceProvider prüfen, dass clientVersion() nicht null ist. Alt: rot. Neu: grün.
